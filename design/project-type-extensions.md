# Third-party project types — extension model

**Status:** v1 shipped, deliberately restricted.
**Scope:** `src/project-types/`, loaded from `~/.claude-terminal/project-types/`.
**Audience:** anyone about to widen this. Read the *Refused* section before you do.

---

## The problem this note exists to answer

`src/project-types/base-type.js` + `registry.js` is already, structurally, a plugin
architecture: a descriptor with ~30 hooks, merged over a set of defaults, looked up by
id. It is simply closed — only the seven types shipped in the repo can exist.

Opening it means deciding what a third-party author is allowed to run, and where. A
project type has two halves and they are not equally dangerous:

| Half | Where it runs | What it gets |
|------|---------------|--------------|
| `main/*Service.js`, `main/*.ipc.js` | Main process | Unrestricted Node: `child_process`, `fs`, `net`, the whole machine |
| `renderer/*Dashboard.js`, `*Wizard.js`, `*TerminalPanel.js`, `*State.js` | Renderer | The full `window.electron_api` surface — 322 IPC handlers — plus `window.electron_nodeModules.fs` |

Neither is "just a bit of UI".

---

## What was actually found in the tree

Two facts changed the design, and both are worth stating because neither is obvious from
reading `registry.js`:

1. **The registry is renderer-only in practice.** `registerAllMainHandlers()`,
   `initializeAll()`, `cleanupAll()` and `getAllPreloadBridges()` exist in `registry.js`
   and are **called by nobody**. The main-side half of every built-in type is wired by
   hand in `src/main/ipc/index.js` and `src/main/services/index.js`. So there is no
   main-process extension path to open — there is only one to *invent*, and inventing one
   is a strictly larger commitment than reusing an existing seam.

2. **The renderer bundle is static.** `registry.discoverAll()` is a list of literal
   `require()` calls precisely because esbuild resolves them at build time. A path under
   `~/.claude-terminal/` cannot be `require()`d from the renderer at all. Loading
   third-party renderer code would mean `new Function(source)` — and the app's CSP is
   `script-src 'self' 'unsafe-eval'`, so **that would work**. The naive implementation is
   the dangerous one, and nothing in the build would have complained.

---

## Decision

**v1 executes no third-party JavaScript, in either process.**

An extension is a **declarative manifest** plus optional translation files. The main
process reads it, validates it, sanitizes it, and hands the renderer plain JSON. The
renderer builds a type descriptor out of that JSON using **first-party code only**
(`src/project-types/external-type.js`). At no point is attacker-controlled text turned
into a function, a module, or a command line.

### What an extension CAN do

- Appear in the new-project wizard and the project sidebar with its own name,
  description, category, icon and accent colour.
- Ship its own translations for those strings, in the app's five locales.
- Declare **detection markers** — file and directory names (`Cargo.toml`, `go.mod`) that
  identify a folder as being of this type. The markers are matched by first-party code;
  the extension supplies names, not code and not globs.
- Declare a short badge label shown on the project card.

### What an extension CANNOT do, at all

- Run code. No `require()`, no `new Function`, no `eval`, no `<script>`, no worker.
- Register an IPC handler, a preload namespace, or a main-process service.
- Run a shell command, a quick action, a dev server or a build step.
- Ship raw CSS. Colour is a single validated hex token; the stylesheet is generated by
  first-party code from a fixed template.
- Read or write any file. The only disk access is the app reading the extension's own
  directory, non-recursively, with a size cap.
- Reach the network. Nothing in the loader fetches; there is no URL field in the manifest
  and no install-from-URL path. **Local disk only, always.**
- Define an i18n key outside its own `ext.<id>.*` namespace, or define any leaf other
  than `name` / `description`. An extension cannot reword "Bypass permissions".

## The three injection sinks, and what closes each

These are the concrete places extension-controlled data reaches the DOM. Each was checked
in the tree, not assumed.

**1. `renderer.js:4933` — ``badge.innerHTML = `…${tp.icon}…${t(tp.nameKey)}…` ``**

Raw `innerHTML`, no escaping, for both the icon and the translated name. This is the sink
that decides the whole validation policy.

- *Name / description:* validated as **plain text** — rejected outright if they contain
  `<`, `>` or `&#`. Not escaped-on-render (an escape at one of N call sites is a bug
  waiting for the N+1th), but rejected at load, once, at the boundary.
- *Icon:* validated as SVG against a tag/attribute allowlist. `<script>`,
  `<foreignObject>`, `<image>`, `<use>`, `<a>`, any `on*` attribute, any `href`/`src`, any
  `url(`, any `javascript:` or `data:` — all rejected. Single `<svg>` root, 4 KB cap.

Note what the CSP already does here and what it does not. `script-src 'self'` with no
`'unsafe-inline'` blocks both `<script>` in injected HTML *and* inline `on*` handlers, so
even an unsanitized icon could not execute JavaScript. The allowlist is defence in depth
against the residual risk, which is real but lesser: UI redressing — an SVG that paints a
convincing fake dialog over the app.

**2. `QuickPicker.js:272` — already guarded**, with an inline `startsWith('<svg')` plus a
`/<script|<foreignObject|on\w+=/` check. v1's validator is a superset of that guard and
runs earlier, so the quick picker is safe by the time it looks.

**3. Generated stylesheet.** CSS under this CSP cannot execute script, but it can
reposition and recolour arbitrary elements. Closed by not accepting CSS: the manifest
offers `color`, matched against `/^#[0-9a-f]{6}$/i`, interpolated into a fixed template
whose selectors are all scoped to `.ext-<id>`.

## Consent model

Four independent gates, all of which must pass:

1. **Off by default.** `projectTypeExtensionsEnabled` defaults to `false` in
   `settings.state.js`. A fresh install loads nothing, ever.
2. **Per-extension opt-in.** Even with the master switch on, an extension only registers
   if its id is listed in `enabledProjectTypeExtensions`. Dropping a directory into
   `~/.claude-terminal/project-types/` makes it *appear in a list as disabled*; it does
   not make it active.
3. **Visible and reversible.** `project-types:list-extensions` returns every discovered
   extension — enabled, disabled, incompatible or broken, with its problems — so the UI
   can show all of them and offer a toggle per extension. Disabling is a settings edit,
   with no uninstall step and nothing left running.
4. **Local disk only.** There is no fetch, no marketplace, no install-from-URL. The user
   put the directory there, with their own file manager. This is the difference between
   "an extension I chose" and "an extension a web page chose for me", and v1 keeps it.

The gate is enforced **twice**: the renderer checks settings before asking, and
`ProjectTypeExtensionService` re-reads `settings.json` read-only and refuses to mark any
entry enabled if the master switch is off. A renderer bug must not be sufficient to turn
the feature on.

## Compatibility and versioning

- `manifest: 1` — the manifest format version. An unknown value is rejected outright
  rather than best-effort parsed; a v2 manifest read as v1 is exactly how a field gets
  silently ignored.
- `engines.claudeTerminal` — a range against the app's `package.json` version. Supported
  forms: `*`, `1.3.2`, `>=1.3.0`, `^1.3.0`, `~1.3.0`. Deliberately a small hand-rolled
  subset rather than a semver dependency: the range lives in an untrusted file, and the
  parser for it should be something a reviewer can read in one sitting.
- An extension targeting an incompatible version is **listed with
  `status: 'incompatible'` and not registered**. It is not silently dropped — the person
  who wrote it needs to see why it did not load — and it is not loaded anyway.

---

## Failure isolation

A broken extension must never prevent the app from starting or break an unrelated panel.
The loader therefore:

- reads and validates each extension inside its own `try`/`catch`; one throw removes one
  extension from the result and nothing else;
- **never rejects.** `listExtensions()` resolves with `{ extensions, problems }` even when
  the extensions directory does not exist, is unreadable, or is full of garbage;
- caps what it will read — 64 KB per file, 64 extensions per scan, non-recursive — so a
  hostile directory cannot stall startup;
- reports failures as data: each problem is `{ id, reason, detail }`, surfaced to
  `ErrorLogService` as a `warning` in the `project-types` domain (not `critical` — per
  `ErrorLogService`, `critical` means the app broke) and to the user as a Toast;
- registers valid extensions independently of invalid ones. Three good and one malformed
  yields three registered types and one problem entry.

On the renderer side, `registry.registerExternal()` wraps each descriptor build in its own
`try`/`catch` for the same reason, and returns counts rather than throwing.

## Interaction with the ESLint boundary rules

The boundaries in `eslint.config.js` are what make this design cheap to keep honest, and
the file layout is chosen to sit inside them rather than around them:

| File | Glob it matches | Consequence |
|------|-----------------|-------------|
| `src/shared/project-type-manifest.js` | `src/shared/**` | Node config, **no** boundary rules — shared by main and tests. Contains zero `fs`, zero DOM, zero `electron`: pure functions over strings and objects, which is why it can be shared at all. |
| `src/main/services/ProjectTypeExtensionService.js` | `src/main/**` | `MAIN_BOUNDARY`: may not `require` anything under `renderer/`, and `document` is a lint error. Correct — this file only touches `fs`. |
| `src/main/ipc/project-types.ipc.js` | `src/main/**` | Same. |
| `src/project-types/external-type.js` | *(none)* | Sits beside `registry.js`, which matches no config either (`src/project-types/*/*.js` is one level deeper). Effectively unlinted, so it is written to renderer rules by hand: no `require('fs')`, no `require('electron')`, no reach into `src/main/`. |

The rules also *prove* part of the security claim rather than merely asserting it. The
renderer may not `require('child_process')` — and `child_process` is not in the preload
bridge — so there is no path from the renderer half of a project type to process spawning
even if renderer code were loaded. That property is why the main half is the graver of the
two, and why v1 opens neither.

No `eslint-disable` was added anywhere for this feature. If one becomes necessary to widen
it, that is the signal to stop and re-read this note.

## Refused, and why

### Third-party renderer JavaScript — refused

`new Function(source)` passes the CSP. It would have worked. It is still the wrong thing,
because the CSP is not the boundary being defended here — the *renderer's authority* is. A
renderer script gets `window.electron_api`: terminal creation, git, arbitrary SQL against
configured databases, `electron_nodeModules.fs`. Loading a stranger's script there is
indistinguishable in effect from loading it in main, minus the honesty of saying so.

CLAUDE.md calls the CSP "the app's most important control — it means HTML injected into
the chat cannot execute script". A `new Function` loader does not literally violate that
sentence; it makes it stop mattering, by opening a second door beside the one the sentence
is about. Half-strength versions of this (parse the source, blocklist `electron_api`) are
worse than useless: a blocklist over a Turing-complete language is theatre, and it would
sell the user a safety claim the implementation cannot keep.

### Third-party main-process JavaScript — refused for v1, not forever

`require()`ing extension code in main is "install and run this program". Unlike the
renderer case that is at least an *honest* proposition, and one plenty of editors make.
But it is a much larger commitment than one pass can validate: it needs a real consent
dialog that says what it means, a story for unloading (Node's module cache does not
forget, and a type that spawned a child process has to be cleaned up), crash containment
for a synchronous throw during `registerHandlers`, and an answer for what happens on app
update.

And the seam does not exist yet: `registerAllMainHandlers()` is dead code. Building a
consent model on top of a function nothing calls would mean shipping two unproven things
at once. If this is taken up later, the order is: wire `registerAllMainHandlers()` for the
*built-in* types first, prove it, then decide about third parties.

### Raw CSS — refused

See sink 3 above. Cheap to allow, not cheap to bound.

### Anything remote — refused

No fetch, no catalog, no `installFromUrl`. Every existing marketplace in this app
(`MarketplacePanel`, `McpRegistryService`, `PluginsPanel`) extends *Claude Code*, whose
code already runs with the user's privileges by design. Extending *Claude Terminal* from
the network is a different proposition and does not get to inherit that precedent by
proximity.

## Manifest reference

```tree
~/.claude-terminal/project-types/
└── my-type/
    ├── project-type.json      # required
    └── i18n/                  # optional
        ├── en.json
        ├── fr.json
        ├── es.json
        ├── id.json
        └── zh-CN.json
```

### `project-type.json`

| Field | Required | Rules |
|-------|----------|-------|
| `manifest` | yes | Must be `1`. |
| `id` | yes | `^[a-z][a-z0-9-]{1,31}$`. Registered as `ext-<id>`, so it can never collide with a built-in and is CSS-class-safe. |
| `name` | yes | Plain text, ≤ 48 chars. No `<`, `>`, `&#`. |
| `description` | no | Plain text, ≤ 200 chars. |
| `engines.claudeTerminal` | no | Range; default `*`. |
| `category` | no | One of `general`, `bots`, `gamedev`. Unknown → `general`. |
| `color` | no | `^#[0-9a-f]{6}$`. |
| `icon` | no | SVG, allowlisted tags/attrs, ≤ 4096 chars. An invalid icon is dropped and the extension still loads. |
| `badge` | no | Plain text, ≤ 12 chars. |
| `detect.files` / `detect.dirs` | no | ≤ 16 entries each; each a bare filename — no `/`, no `\`, no `..`, ≤ 64 chars. |

### `i18n/<lang>.json`

```json
{ "name": "Rust", "description": "Cargo-based Rust project" }
```

Only `name` and `description` are read; only the five supported locales are read; the same
plain-text rule applies. Merged as `ext.<id>.name` / `ext.<id>.description`.

A worked example lives at `src/project-types/examples/rust/`. It is deliberately tiny — it
is documentation, not a migration. Extracting FiveM or Minecraft into an extension is a
separate and much larger piece of work, and this manifest format is not yet close to being
able to express them. That is the correct order: prove the mechanism on something small
before deciding what the format has to grow into.
